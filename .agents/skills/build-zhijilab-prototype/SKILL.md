# 构建 ZhijiLab 高保真原型

把产品需求直接实现为可运行、可评审的当前最终态页面。

组件与设计复用顺序、页面目录结构、菜单元数据、页面 `README.md` 内容要求和 Scope Control 全部以工程根目录的 `AGENTS.md` 为准，本文件只定义流程、外部工具和交付方式，不重复其中的约定。

执行顺序：前置检查 → 需求澄清 → 了解平台基础 → 需求评审 → 产品与交互设计 → 页面实现 → 本地验收 → 提交与交付。前一步没有通过就不要进入下一步；需求澄清判定本次不涉及原型开发时，流程到需求澄清为止。

## 1. 前置检查

前置检查脚本需要 Node.js 才能运行。`node --version` 不可用，或脚本无法启动、没有输出任何 `[PASS]` 与 `[FAIL:...]` 行时，说明缺少 Node.js，直接按 [references/preflight-troubleshooting.md](references/preflight-troubleshooting.md) 的 `NODE_MISSING` 处理，不要反复重试脚本。

在工程目录执行前置检查脚本，需求中包含 TAPD 链接时追加 `--require-tapd`：

```bash
node <skill-directory>/scripts/preflight.mjs --project-dir <project-directory>
```

脚本校验 Node.js 版本、npm、Git 与工蜂仓库访问、`origin` 指向、工程身份与必需文件、npm 依赖和初始构建，并报告 mcporter 与 TDesign / TAPD MCP 的配置状态。它只做检查和报告，不执行任何安装或配置。

- 输出 `[FAIL:<CODE>]` 时按 [references/preflight-troubleshooting.md](references/preflight-troubleshooting.md) 中对应的 CODE 处理，修复后重新执行；只有输出 `PREFLIGHT_OK` 后才能继续。
- 输出 `[WARN:<CODE>]` 不阻断流程，但要判断它是否影响本次需求，必要时同样按该文档处理。
- 检查全部通过时不需要阅读该文档。
- 本次只讨论需求或调整需求文档时，只要求读取需求所需的 MCP 可用，依赖与构建相关的检查项不阻断讨论。
- 安装、全局配置、写入 MCP 配置或改动 Git 远端前，必须先向用户说明完整命令并取得明确同意，不得静默执行。
- 使用脚本输出的 `PROJECT_ROOT` 作为后续工作目录，完整阅读其中的 `AGENTS.md`，并保留已有 Git 修改。
- `TDESIGN_MCP` 与 `TAPD_MCP` 只反映 mcporter 的配置状态，智能体已挂载对应原生 MCP 时可以忽略；`TDESIGN_MCP_SERVER` 与 `TAPD_MCP_SERVER` 是 mcporter 中实际的 server 名，用 mcporter 兜底时必须用它们，不要硬编码名称。

## 2. 需求澄清

### 2.1 获取完整需求内容

先拿到完整需求，再做任何判断。

- 逐页提取产品内容、初始状态、用户操作、操作结果、业务约束、开发交接信息和已有文档链接，只保留明确要求。
- 需求正文引用了其他需求、设计稿、接口文档或附件，且这些内容影响页面范围或交互时，同样先读取。
- 需求内容不完整、只有标题或只有片段时，向用户索取缺失部分，不据此推测，也不带着不完整的需求进入下一步。

需求以 TAPD 链接形式给出时，必须读取链接内容，不要求用户重复粘贴文档正文：

- 优先使用智能体已挂载的 TAPD MCP。不可用时才用 mcporter 兜底，server 名使用前置检查输出的 `TAPD_MCP_SERVER`：先执行 `mcporter list <TAPD_MCP_SERVER> --schema --json --timeout 20000` 获取实际工具及参数，再使用 `mcporter call <TAPD_MCP_SERVER>.<tool> ... --timeout 20000` 调用与链接类型匹配的读取工具，不要猜测 server 名、工具名或参数。
- 提取页面范围、业务规则、交互、验收条件及有效关联资料，并把 TAPD 链接记录到对应页面 `README.md`。
- 两种方式都不可用时，不使用网页抓取或臆测内容代替；按 [references/preflight-troubleshooting.md](references/preflight-troubleshooting.md) 处理 mcporter 与 TAPD MCP 配置后重试。
- 太湖令牌只允许存在于用户本机的 mcporter 配置中，智能体不得读取、回显或写入仓库。

### 2.2 确认本次任务类型

三类任务的做法不同，先判断属于哪一类，判断不了就先问用户。

**开发新页面**：根据业务含义拟定简短、可读的英文 kebab-case 路径，并检查 `src/pages` 避免冲突；禁止使用需求编号、日期、团队名以及 `page`、`prototype`、`demo` 等无业务含义的词。一次需求包含多个页面时分别给出路径，仍按独立页面创建，不建立需求级 App 或目录层。集中向用户确认页面中文名称、建议 URL、一级菜单名称和可选的二级菜单名称，得到明确确认后再创建文件；用户已指定的路径视为已确认。

**迭代已有页面**：先定位页面目录，完整阅读它的 `index.tsx`、`README.md` 和实际使用的组件，弄清现有实现以及本次真正要改动的部分。不改动已有 URL、目录名和菜单归属；需求明确要求改动时，按新增页面的方式与用户确认后再改。

**只讨论需求内容或调整需求文档**：不涉及原型开发时，完成讨论或文档修改即可，不执行 2.3 及后续步骤，不创建页面、不改动 `src/pages`，也不进入本地验收和提交交付。

### 2.3 了解平台基础

需要进入原型开发时，在评审需求前完整阅读 [references/platform-basics.md](references/platform-basics.md)，理解 ZhijiLab 平台的固定框架、业务权限与当前业务上下文。该文档集中维护平台基础背景。

### 2.4 需求评审

需要进入原型开发时，先从开发视角评审一遍需求，再动代码。

- **完整性**：页面初始状态、空态、加载与错误反馈、边界值、操作后的状态变化、字段来源和取值范围是否都有交代。
- **合理性**：需求是否自相矛盾，是否与仓库现有设计语言、组件能力和 `AGENTS.md` 的约定冲突。
- **实现成本**：按当前仓库的组件和依赖判断哪些内容成本明显偏高、需要新依赖或超出高保真原型该承担的范围，据此挑战需求内容。

把发现的问题、影响和建议方案集中一次提给用户，指明哪些必须现在定、哪些可以按建议默认处理。只有会改变业务含义、数据结果、权限、页面范围或关键流程的缺口才必须由用户确认；常规布局、反馈方式和组件行为依次按仓库同类页面、TDesign 标准能力和通用管理端惯例自主完成。不得臆造业务规则或默默降级实现。评审确认的结论要保留下来，在第 3 步随页面一起写入页面 `README.md`。

### 2.5 产品与交互设计

进入页面实现前，完整阅读 [references/product-interaction-design.md](references/product-interaction-design.md)，依据其中的原则完成当前页面的产品与交互设计，并确定本页需要实现和验收的预览场景。设计方案与场景范围没有收敛时，不进入页面实现。

若设计过程中发现会改变业务含义、数据结果、权限、页面范围或关键流程的缺口，回到 2.4 集中向用户确认；纯设计决策按参考文档和仓库既有设计语言自主完成。设计结论直接落入当前最终态页面，需要开发者知晓的业务规则、场景含义和交互结果随页面写入 `README.md`，不额外创建设计说明文档。

## 3. 页面实现

页面怎么写以 `AGENTS.md` 为准，这一步只约束推进方式。

开始写代码前先同步远端：确认当前分支为 `main`，检查并保留已有修改，执行 `git pull --rebase origin main`。已有修改阻碍同步时先妥善处理，不得丢弃或覆盖。拉入了远端改动时重新确认依赖并执行一次 `npm run build`，确认基线仍然可用再开始写代码。

- 以页面为推进单位。一次需求包含多个页面时，一个页面达到完成条件后再开始下一个，不同时留下多个半成品页面。
- 单个页面的完成条件：页面入口、`components/` 中的页面组件、`meta.ts`、`scenarios.ts` 和页面 `README.md` 都是当前最终态，全部预览场景可通过全局切换器进入，并且 `npm run build` 通过。2.4 和 2.5 中影响开发实现的结论在这一步写入页面 `README.md`。
- 先按业务区域划分页面组件再写各区域细节，不先把实现堆进 `index.tsx` 再考虑拆分。每完成一个区域就确认它的文件规模和状态归属符合 `AGENTS.md` 的页面内组件拆分约定。
- 优先使用工程已有组件，避免重复实现和引入新依赖。产品结构和交互方案根据用户任务与业务规则确定；视觉表达、组件行为和基础交互优先遵循仓库既有模式及 TDesign 能力。
- 视觉样式优先使用 `src/design-tokens/tdesign-theme.css` 提供的系统主题变量，不自行硬编码颜色或重写 TDesign 组件样式；只有需求明确要求时才添加自定义视觉样式。
- 使用工程内置 `definePageScenarios` 和 `usePageScenario` 接入页面场景。场景驱动真实组件、Mock 数据和初始交互状态，不在页面内自制切换器，不用截图、说明文字或重复页面模拟状态。
- 实现过程中发现需求缺口、规则冲突或与仓库现有实现矛盾时，停下来回到 2.4 与用户确认后再继续，不自行假设补齐。

### TDesign 组件使用

- 需要确认 TDesign 组件的属性、事件和用法时，优先使用智能体已挂载的 TDesign MCP；不可用时用 mcporter 兜底，server 名使用前置检查输出的 `TDESIGN_MCP_SERVER`，先执行 `mcporter list <TDESIGN_MCP_SERVER> --schema --json`，再使用 `mcporter call <TDESIGN_MCP_SERVER>.<tool> ...`。MCP 只用于查阅组件能力，最终实现以仓库安装的版本、类型定义和现有组件为准，两者不一致时以仓库为准。都不可用时停止相关步骤，并按 [references/preflight-troubleshooting.md](references/preflight-troubleshooting.md) 与用户确认配置，不得模拟 MCP 结果。
- TDesign MCP 提供 `get-component-docs、get-component-list` 工具，分别用于获取组件文档和组件列表。

## 4. 本地验收

- 先自查本次变更代码及 `git diff`，逐项对照原始需求和 `AGENTS.md`，确认没有解释性页面内容、需求外功能、补丁式实现、失效代码或遗漏的页面 `README.md` 更新；逐项切换 `scenarios.ts` 中声明的场景，确认表现与说明一致、状态切换会重置页面且场景内真实交互仍成立。发现问题先修正。
- 检查页面结构：`index.tsx` 只承担场景装配、跨区域状态与组件编排，没有用 `renderXxx` 闭包代替组件，没有超出 `AGENTS.md` 规模上限的文件或组件函数。超标时先完成拆分再继续验收。
- 再次对照 [references/product-interaction-design.md](references/product-interaction-design.md) 检查当前页面实现；发现不符合项时回到第 3 步修改，复查通过后再继续验收。
- 自查通过后执行 `npm run build`，修复所有类型和编译错误。
- 编译通过后执行 `npm run dev` 并保持运行，使用终端实际输出的地址拼接页面路径，向用户提供可访问的本地链接。列出 `scenarios.ts` 中的全部预览场景，并明确提醒用户逐项验收每个场景的视觉表现、状态语义和场景内交互；不能只提供默认场景。后续修改由 Vite 热更新生效，不重启 dev，也不重复发送同一个链接。
- 视觉与交互由用户在浏览器中人工检查，不使用自动化操作代替。用户没有明确确认全部预览场景通过前，不进入第 5 步。
- 收到反馈后先判断类型：属于实现或视觉问题，回到第 3 步修改；暴露出需求理解偏差或规则缺失，回到 2.4 与用户确认后再改。每轮修改后重新自查并构建。

## 5. 提交与交付

- 用户完成人工检查并确认后，只暂存本次需求范围内的文件，提交到 `main` 并执行 `git push origin main`。始终直接在 `main` 工作，不创建功能分支，不使用多分支或多工作树流程。
- 发生拉取、rebase 或推送冲突时，先理解远端与本地改动，逐处合并为正确的当前最终态，再重新构建、继续 rebase 并推送。禁止强制推送、reset 或整文件选择 ours/theirs 粗暴覆盖。
- Commit Message 使用conventional commits 规范，包括类型、作用域和描述。标题和内容使用中文，描述清楚本次变更范围和内容。
- 推送成功前，不得将任务描述为已交付。
- 推送成功后，在最终回复中给出面向开发者的交付总结，不额外创建总结文档。每个页面一段：

```markdown
### <页面中文名称>
- 访问路径：<URL>
- 代码目录：src/pages/<code-path>/
- 变更内容：<页面结构、组件复用、交互、数据和页面 README 的实际变更，一到三句>
```

交付总结只描述已经提交并推送到 `main` 的当前最终态，并准确列出实际可切换的全部预览场景；不附加过程说明、未执行建议、TODO、未来计划或需求外内容。
